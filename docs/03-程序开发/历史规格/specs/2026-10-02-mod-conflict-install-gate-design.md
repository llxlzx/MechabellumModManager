# 互斥 Mod 安装门闩

**日期：** 2026-10-02

伤害排名（`damage-rank`，巴巴）和钢铁战局助手（`battle-suite`，老匪_GODOG）都做伤害排名。两个一起装进游戏会坏。管理器在玩家往本地库里加入第二个时拦住，说明原因，不下载、不入库。想装另一个，先卸载已在库里的那个。

## 已确认的行为

- 拦住安装，不提供「仍然安装」按钮。
- 已经两个都在库里的，打开管理器时不提醒，启用和应用方案也不改。
- 更新已经在库里的那一个，即使另一个也在库里，仍然允许。

## 目录字段

每个 mod 可选 `conflicts`。没有这个字段、或是空数组，表示没有互斥。

```json
"conflicts": [
  {
    "id": "battle-suite",
    "reason": "两者都包含伤害排名，同时安装进游戏会坏。",
    "locales": {
      "en": { "reason": "Both include a damage ranking. Installing them together breaks the game." },
      "de": { "reason": "Beide enthalten eine Schadensrangliste. Gleichzeitige Installation macht das Spiel kaputt." },
      "ja": { "reason": "両方にダメージ順位があり、同時に入れるとゲームが壊れます。" },
      "ru": { "reason": "Оба показывают рейтинг урона. Вместе они ломают игру." }
    }
  }
]
```

- `id` 是对方的目录 id。比较时忽略大小写并去掉首尾空白。
- `reason` 是默认说明（简体中文）。`locales` 只覆盖说明，键与现有简介相同：`en`、`de`、`ja`、`ru`。界面语言对得上就用该语言的 reason，否则用默认 reason。
- 空 id、指向自己的 id、目录里不存在的 id，运行时忽略。
- 同一 mod 里重复指向同一个对方，保留第一条。
- 关系是无向的。只写在一边也两边都拦。`scripts/validate_catalog.py` 要求对称：A 列出 B 时 B 必须列出 A，且不能指向自己或不存在的 id。

本仓库的 `MechabellumMods/catalog.json` 给 `damage-rank` 和 `battle-suite` 互相写上上面这条说明。目录 `updatedAt` 前进。旧版管理器忽略未知字段，行为不变。

## 「已在库」

沿用 `ModCatalogService.Matches` / `IsInLibrary`：目录 id、文件 sha256，或可区分的 Melon 程序集名加作者。在库即可，不看方案里有没有启用。禁用仍算已安装。卸载指从本地库删除（现有删除），不是只关掉启用。

对不上目录的 DLL（哈希、目录 id、程序集名都对不上）不参与互斥。这是既有的「这是哪一个目录 mod」判断，门闩不另做一套。

## 判定

纯函数 `ModConflictGate.Evaluate`。输入是当前目录、**这次操作之前**的本地库、以及这次想加入或更新的目录 id。输出是允许继续的 id，以及被拦住的记录（要装的 id、挡住它的对方 id、原因是「对方已在操作前的库里」还是「对方也在这次新装集合里」、两边的本地化名称、选用的说明；说明为空表示用通用句）。

一次请求里的 id 分成两类：

- **已在库**：更新或已是最新。一律允许。不因为互斥被拦住。
- **新装**：库里还没有。

新装的 F 被拦住，当且仅当某个互斥对方 P（沿任一边的 `conflicts`）满足：P 已在操作前的库里，或 P 也在这次的新装集合里。

因此：

- 只新装 F，P 已在库：拦住 F。P 的更新若同时在这次请求里，仍然允许。
- 一次勾选两个互相冲突、库里都还没有的：两个都拦住。同一次请求里不冲突的其他 mod 照常安装。
- A 只和 B 冲突、B 只和 C 冲突时，只勾选 A 和 C：两个都装。勾选 A、B、C：三个都拦住，因为每一个的对方都在这次新装集合里。玩家再勾一次只留能共存的。
- 不再额外做连通分量。A、B、C 一起被拦住，只是因为每一对的对方都在这次新装集合里。

说明的选取顺序：F 指向 P 的 reason（按界面语言），否则 P 指向 F 的 reason，否则空，交给通用句。名称用 `CatalogLocaleResolver.ResolveName`。成对文案只出一次时，用两条记录里第一条非空说明；都空则用通用句。id 按忽略大小写排序后的顺序写进「甲和乙」，保证同一对的句子稳定。

## 文案

一次请求只弹一个确定框（现有 `_notify`），不逐条弹。同一次请求里可以同时出现下面两种句子：有的被库里已有的对方拦住，有的因为这次一起勾选而被成对拦住。

对方已在库时，每一条：

`不能安装「{incoming}」。已安装的「{partner}」与它冲突。{reason}请先卸载「{partner}」。`

reason 非空时句末带它；为空时改用：

`不能安装「{incoming}」。已安装的「{partner}」与它冲突，不能同时安装。请先卸载「{partner}」。`

两个都是新装、因此成对拦住时，每一对只出现一次（无序）：

`「{a}」和「{b}」不能同时安装。{reason}请只选择其中一个。这次都没有安装。`

reason 为空时：

`「{a}」和「{b}」不能同时安装。请只选择其中一个。这次都没有安装。`

多条之间换行。同一句写进日志。壳句放 `Strings.resx` 及 en/de/ja/ru。目录里的 reason 不放进 resx。

## 接入点

**目录加入本地库**（`AddCatalogModToLibraryAsync`）：在下载之前对本次全部目标做一次判定。被拦住的不下载、不入库、不进入高风险确认。允许的才逐个走现有下载、导入、更新。只看单个 `AddOneCatalogModAsync` 会把一对里先处理的那个装上，再拦住第二个，这违反「两个都是新装时都不要装」。因此成对规则放在这一次批量判定里。`AddOneCatalogModAsync` 自己再拦一层：新装对象在操作前的库里已有互斥对方时直接返回。单条更新入口因此也不会把新装插进去，但单条入口看不到同批的另一个新装，那条规则只由批量判定负责。

**单 DLL、压缩包、文件夹导入**：导入完成后、启用之前判定。刚导入的包从库快照里拿掉，作为这次请求的目录 id（一个包 `Matches` 到哪些目录 id 就请求哪些）。判定拦住的 id，对应的新包 `Delete` 掉，不启用。对不上任何目录 id 的包留下并照常启用。一个包只要匹配到任一被拦住的 id 就删除。`Delete` 失败时记日志，并且不启用该包。

**游戏目录扫描导入**不走这道门闩。扫描是在认游戏里已经有的文件，不是玩家挑选安装。两个 DLL 已经在游戏里时，拦扫描不能避免进游戏会坏，还会让库里少看到一个已经在磁盘上的 mod。

启用、禁用、应用方案、启动游戏不改。

## 测试

`ModConflictGate` 的单元测试覆盖：

- 对方已在库时拦住新装
- 对方已在库时仍允许更新自己
- 库里已有时，禁用与否都算已在库（判定只看包列表，不看方案）
- 一次请求里两个新装互斥：都拦住；同批不互斥的第三个放行
- A–B、B–C 的链：只请求 A 和 C 时都放行；A、B、C 一起请求时都拦住
- 只写在一边的边，两个方向都拦
- 指向自己、空 id、目录中不存在的 id 被忽略
- 重复边用第一条的说明
- 说明回退：界面语言、默认 reason、反向边、最后为空
- 名称走目录本地化
- 文案把「已在库」和「两个都是新装」分成上面的两种句式，成对只出现一次
- 导入场景：把新包排除出「操作前的库」之后，互斥的两个新包都被标成拦住

`validate_catalog.py` 对缺少对称、指向自己、指向未知 id 报错。现有目录加上这两条之后校验通过。

## 逻辑自检（写入前的漏洞和裁定）

1. **整团拦住会误伤链。** A–B、B–C 时，把连通分量全部拦住会让可以共存的 A 和 C 也装不上。改为只看成对：对方在库里，或对方也在这次的新装集合里。
2. **导入之后库里已经有新包。** 若用导入后的库调用判定，新包会被当成「已在库的更新」而放行。判定的库必须是这次操作之前的；导入路径把刚导入的包从库快照里拿掉。
3. **先下载再删会留下半截文件，还会先弹出高风险确认。** 目录安装在下载之前判定。
4. **一批多个弹窗。** 合并成一个 `_notify`。
5. **游戏扫描不该用这道门闩。** 见上文接入点。已经两个都装在游戏里的玩家，这次不强制拆开。
6. **更新不能被互斥误伤。** 已在库的 id 一律允许，包括两个互斥 mod 都已经在库时各自更新。
7. **只写一边的目录。** 运行时无向，校验要求对称，避免发布出单边数据。
8. **启用状态。** 「已安装」是本地库里有这份包，不是当前方案启用了它。只禁用不够，必须卸载。
9. **身份不另造。** 复用 `Matches`。改过名或对不上哈希的非官方 DLL 不会被拦住。这是限度，不是漏判官方文件。
10. **说明为空仍要能拦住。** 壳句有不带 reason 的通用形式。
11. **`Delete` 失败。** 不启用该包，避免拦了提示但方案里仍然打开它。
12. **目录还没加载。** 没有目录条目时不拦导入。互斥数据在目录里，没有目录就没有边。
13. **文案两种原因可以同时出现。** 初稿写成「没有新装对子时才用卸载句」，一批里既有已在库的对方、又有一起勾选的对子时会丢一种说明。两种句子按拦住原因分别输出。
14. **批量入口和单条入口分工。** 只在 `AddOne` 里按当前库判断，会先装上一对中的第一个。成对规则必须在下载前对整批做完。`AddOne` 只再挡「对方已经在库里」的新装。
15. **成对文案的说明来源要稳定。** 两条方向可能都有记录。用第一条非空说明，名称按 id 排序，避免同一次判定句子不一样。
16. **导入包可能匹配多个目录 id。** 任一被拦住就删除该包，避免哈希对上一个、程序集名对上另一个时漏放。
