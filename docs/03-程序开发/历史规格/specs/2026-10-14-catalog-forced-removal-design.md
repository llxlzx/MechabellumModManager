# 目录强制下架 Mod

**日期：** 2026-10-14（同日按自检结果修订：加签名、修双服、修兜底删除、补应用前检查）

**范围：** 管理器按维护者签名的下架名单，把命中的 Mod 从玩家机器上移除。安装器不参与。

## 目标

维护者签发一份下架名单后，玩家下一次启动、刷新目录、导入 Mod 或应用方案时，管理器把命中的 Mod 从三处移除：

1. 本地库里的包（包目录、索引）
2. 所有方案里的勾选
3. 游戏目录里这个 Mod 的副本，前提是能确认字节：部署记录里的哈希、包自己的文件哈希，或名单上的哈希

## 不做的事

- 不按 DLL 名称或 MelonInfo 名称匹配，不删字节无法确认的文件（玩家自己改过的同名 DLL 保留）。
- 安装器端不加清理步骤。
- 不做下架历史页面，只有日志和一次性提示。

## 信任模型：为什么必须签名

镜像（COS）返回的 `catalog.json` 可以胜出，所以只要镜像被攻破，没有签名时任何人都能往名单里加条目，批量删除玩家的 Mod。现在：

- 名单用维护者私钥离线签名（ECDSA P-256 / SHA-256），管理器用编译进程序的公钥 `RemovalListVerifier.PublicKey` 校验。镜像能转发名单，但无法新增或修改任何一条。
- 公钥为空时任何名单都不生效（失败即关闭）。在维护者生成密钥、填入公钥并发布那个版本之前，下架不会对任何玩家生效。
- 防回滚：名单带签名时间 `issuedAt`。管理器把已采用的名单单独存成 `removal-list.json`，比它旧的名单不会替换它。所以镜像同步滞后、或攻击者重放旧名单，都不能撤销已生效的下架。这个文件也不随升级时清空的目录缓存一起消失。
- 私钥泄露等于任何人都能下架。私钥只放在仓库之外（工具会拒绝把私钥写进任何 git 工作区），离线备份。

## 数据

### 维护者编辑的源文件：MechabellumMods 根目录 `removed.json`

```json
[
  {
    "id": "opponent-economy",
    "name": "Opponent Economy",
    "sha256": ["<发过的每个版本的哈希>"],
    "reason": "影响对局公平，已下架",
    "since": "2026-10-14",
    "locales": { "en": { "reason": "Affects match fairness; removed" } }
  }
]
```

### 发布的内容：`catalog.json` 顶层 `removedSigned`

```json
"removedSigned": { "payload": "<base64>", "signature": "<base64>" }
```

- `payload` 是 `{"issuedAt":"…Z","removed":<removed.json 原文>}` 这段 UTF-8 字节的 base64。签名针对这段原始字节，不需要对 JSON 做规范化。
- `signature` 是 64 字节的 r||s（IEEE P1363）。
- `tools/sign-removed.ps1` 生成这个对象并写进 `catalog.json`，目录里的其余文本逐字节不变。签名前它会做与客户端相同的检查：id 仍在 `mods` 里、哈希仍被上架 Mod 发布、空文件哈希、格式不对的哈希、超过 1 MiB，都拒绝签名。签名时间与区域格式无关，必须晚于已发布的名单，且不能超过当前时间 10 分钟以上。
- 公钥必须是 P-256 曲线上的点。粘错的公钥（包括曲线外的 64 字节）按「没有公钥」处理，只会关闭下架，不会让目录刷新报错。打包脚本在公钥为空时给出警告。
- 不带签名的 `removed` 字段不会被读取。旧版管理器两者都忽略。
- MechabellumMods 的 `validate_catalog.py` 只检查 `mods`，`stamp_hashes.py` 逐行改写，两者都不会拒绝或丢掉这个新字段。管理器内的 `MirrorCatalogPublisher` 回写时逐字节保留，有测试覆盖。

## 名单清洗（`ModRemovalGate.Sanitize`）

签名通过后，执行前再清洗一次：

- 哈希只接受 64 位十六进制，统一转小写。空文件的哈希 `e3b0c442…b855` 一律拒绝，否则任何含空文件的包都会命中。
- 目录 `mods` 里仍在上架的 Mod，其 `sha256` 与 `bundle[].sha256` 从名单里扣掉，并记一条警告。改名迁移时，旧 id 的历史哈希里会包含新 id 正在发的 DLL，这样新 id 不会被反复删除。
- 既没有 id 也没有合法哈希的条目丢弃。

## 匹配规则

- 本地库包命中：`CatalogId` 或包 id 等于条目 `id`（忽略大小写），或任一文件哈希在名单里。
- 部署记录条目命中：属于命中的包，或条目哈希在名单里（用来清掉库里已删、游戏目录还残留的副本）。
- 同一个 id 同时在 `mods` 和名单里时按下架处理：目录列表不显示它，启动时也不会提示它「有新版本」，警告只记一次。

## 执行（`ModRemovalEnforcer`）

调用方传入部署记录与它们实际所在的物理目录（`DeployTarget`）：

- 单目录：`deploy-manifest.json`，用它自己记录的 `GamePath`；没有部署记录时按当前游戏目录查找副本。
- 双服（`BranchSwitchConfig.Enabled`）：`deploy-manifest.official.json` 对应 `OfficialStorePath`，`deploy-manifest.beta.json` 对应 `BetaStorePath`；没有部署记录时两个仓都查。
- 为什么不用记录里的路径：双服模式下两份记录写的都是 Steam 链接（junction），它只指向当前挂载的仓，会把未挂载的那个仓误判为「文件已不存在」。

步骤：

1. 游戏正在运行：本次什么都不动，记为延后。
2. 每个命中条目：
   - 目录不可达（仓不存在、存储路径为空）：保留条目、整包延后。目录都到不了，就不能断定文件已经没了。
   - 路径越出该目录、文件不存在、或字节与记录不同：只去掉条目，不删文件。
   - 字节与记录一致：删除并去掉条目；删除失败（文件被占用）则保留条目、整包延后。
3. 没有部署记录的包：在查找目录里按「这个 Mod 在游戏目录里应在的位置」找文件，只有字节等于包自己的文件哈希或名单哈希时才删。旧的按文件名删除的兜底不再使用。双服模式下任一仓不可达时整包延后；单目录模式下游戏目录不存在则不查（那里不会有副本）。
4. 在拿到当前目录（或目录缓存）之前，不知道哪些哈希仍被上架 Mod 发布，所以只按 id 执行，只靠哈希命中的条目等目录到了再执行。升级后首次离线启动属于这种情况。
5. 构造期间（窗口还没显示）产生的下架提示先暂存，启动检查开始时再弹出，因为对话框不能挂在尚未显示的窗口上。
6. 整包没有延后时，执行 `ModLibraryService.Delete`：删包目录、索引，并去掉所有方案勾选。

延后时连库也不删：名单可能只写 id、不写哈希。包留着，下次仍能按 id 命中，把游戏目录副本一起清掉。

## 挂接点（`MainViewModel`）

- 目录到达（`ApplyCatalogRootCore`）：校验并采用签名名单 → 执行 → 构建目录行 → 两份列表都刷新后才弹提示（提示是模态框）。
- 导入 DLL / Zip / 文件夹之后：先执行，再只对仍然存在的包询问启用，避免为一个马上要删掉的 Mod 弹高风险确认。从游戏导入之后也执行。
- 应用方案（含应用并启动）：先执行一次；部署时再把仍命中名单的包从部署集合里排除。即使本次执行被跳过（文件被占用、会话锁），也不会把它部署出去，规划器还会删掉记录里它的旧副本。
- 跳过条件：关键操作进行中、会话锁（分支向导、Steam 结算、恢复门、带会话锁的任务）、存在中断操作待恢复。名单已经存好，下次自动重试。
- 「启动时检查 Mod 更新」关闭时，启动仍拉取目录并执行下架，只是不统计、不提示更新，也不记网络提示和陈旧镜像日志。
- 延后、同时上架与下架、名单被拒、哈希被忽略这几类日志，每次会话每条只记一次。

## 安装器相关的一处修正（与国内/国际包设计配套）

安装末尾下载运行时组件时，线路 1（始终国内镜像）传 `--route-mirror`，直接走镜像，不再做地区探测。线路 2 或镜像地址已清空时传 `--no-mirror`；线路 0 不传，由管理器自动判断。这几个参数都是固定字符串，不会把 `config.json` 里的文本拼进命令行。玩家自定义的镜像地址不传给安装期下载，安装期始终用内置默认镜像。

## 测试

- `RemovalListVerifierTests`：正确签名通过；改过的载荷、其他私钥签的名单、缺签名或编码错误、缺 `issuedAt`、超大载荷都拒绝；没有公钥或公钥非法时一律拒绝；发布的公钥要么为空，要么是 64 字节的点。
- `RemovalSigningToolTests`：在 Windows PowerShell 里实际运行签名脚本，签出的名单由 .NET 8 校验通过；再次签名会替换旧名单；目录其余文本不变；拒绝把私钥放进任何 git 工作区或管理器仓库；拒绝格式不对的哈希。
- `ModRemovalGateTests`：按 id、包 id、哈希命中；只有显示名相同不命中；清洗规则（格式、空文件哈希、仍在上架的哈希）。
- `ModRemovalEnforcerTests`：删除记录一致的副本；记录不一致的同名文件保留；双服两份记录都写 junction 时两个仓都清；仓不可达时保留并延后；文件被占用时整包延后；没有记录时同名不同字节的文件保留、名单上的字节照删；路径越出目录不删；游戏运行时全部延后。
- `MainViewModelCatalogRemovalTests`：签名名单生效；其他私钥签的名单、没有公钥都不生效；旧名单不替换新名单；延后日志只记一次；应用方案时完成延后的下架而不是重新部署；恢复门期间不动、解除后重试；同时上架与下架的 id 不显示；关闭更新检查时启动仍执行；导入被下架的 DLL 不会被启用；已采用的名单在重启、目录缓存被清空后仍然有效；仍在上架的哈希不执行；真实 junction 下未挂载仓的副本被删除。
- 变异验证：把双服映射改回「用记录里的路径」、或去掉应用前检查，对应测试都会失败。
- `EnsureRedistCliTests` 与 `InstallerScriptContractTests`：安装期线路参数；用临时 Setup 实际跑过安装器的线路判断，5 种情况结果正确。

## 上线前必须做的事

1. 运行 `tools/sign-removed.ps1 -NewKey -KeyFile <仓库外路径>`，把输出的公钥填进 `RemovalListVerifier.PublicKey`，并离线备份私钥。
2. 发布带这个公钥的管理器版本。
3. 之后每次下架：编辑 `removed.json` → 运行签名脚本 → 提交 `catalog.json` 与 `removed.json` → 同步镜像。
