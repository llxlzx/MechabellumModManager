# 四目标 Mod 总路线图

**Status:** Approved 2026-10-14（方案 A + 单轨验收门闩）  
**Scope:** 优先级、依赖、风险与开规格顺序；不含单个 Mod 的实现细节。

## 背景

社区反馈与自拟目标共四条线：

1. 聊天相关（Discord：滚底 / 悬停开窗 / 加载刷新丢输入 / 多窗共享删消息；另有外置翻译与 txt 词替换想法）
2. 对局内自禁单位与增援选择（只限自己）
3. 对称布阵辅助（中线 + 到轴垂直距离；地图本身不对称）
4. 自动领取商店信用点

本仓库是 **Mod 管理器**；游戏侧 MelonMod 按 [MechabellumMods `ai-mod-standard`](https://github.com/llxlzx/MechabellumMods/blob/main/docs/ai-mod-standard.md) 交付 DLL 与目录字段。本路线图只规划顺序与边界，不在此仓库实现 Harmony 补丁。

## 工作方式（硬门闩）

- **单轨：** 同一时间只推进一个目标（一份功能规格 → 实现 → 验收）。
- **完成再决定下一个：** 当前目标在游戏内验收通过、无阻塞问题之后，再决定是否开下一个规格；不并行开多个实现。
- **规格拆分：** 每个目标单独一份 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，批完再写实现计划。
- **图 1–3 拆开：** 「聊天 UX」与「翻译 / 词替换」分属不同目标，不做成一个全能包。

## 优先级方案

曾比较三种排期，采纳 **方案 A（风险升序）**：

| 序 | ID | 目标 | 理由 |
|----|-----|------|------|
| P0 | auto-claim-credits | ④ 自动领信用点 | 纯商店/UI 客户端操作，风险最低，易验收 |
| P1 | placement-assist | ③ 对称布阵辅助 | 叠加层 QoL；可对照现有格线/轴锁定；先分析再实现 |
| P2 | chat-ux | ① 聊天 UX（仅 Miragee 四条） | 社区痛点强，但 Chat 状态机难摸、版本脆 |
| P3 | self-unit-ban | ② 自禁单位/增援 | 必须严格 UI 过滤；误挂钩协议易 Data Error |
| P4 | chat-translate / word-swap | ① 延伸：外置翻译 + txt 词替换 | 依赖文本钩子与外部服务/词表；聊天 UX 完成后再开 |

未采纳：B（聊天优先，易卡在反编译）、C（四份分析全写完再动手，缺少早期可玩成果）。

## 分目标：依赖与风险

### P0 — 自动领取信用点

- **范围：** 监视信用点面板；达阈值或定时触发「领取」；可开关。
- **依赖：** 反编译定位领取入口与进度字段；无其他目录 Mod 硬依赖。
- **风险：** 低（客户端商店操作）。需避免误触未打开面板时的空引用；不改战斗演算。
- **目录：** 新 `id`（建议 `auto-claim-credits`）。

### P1 — 对称布阵辅助

- **范围（开 P1 规格时必须覆盖）：**
  1. 高亮地图中央轴；放置过程中显示当前单位中心到该轴的垂直距离（原社区诉求）。
  2. 显示正在放置/选中的单位相对**已放置单位**的距离（VoidInsanity 2026-10-14 补充：「For 3, possible to display distance from unit being placed/selected relative to placed units?」）。
  3. 不承诺地图几何 100% 对称下的完美镜像。
- **UI 方向（已确认）：** 部署时要有真实「格点 + 距离数字」的读数感（社区色块图仅作概念参考）。**不用**聊天 emoji 实现。可与现有 `show-grid` 并存或复用格线习惯，具体热键/样式在 P1 功能规格里定。
- **依赖：** 部署阶段坐标与叠加绘制；可参考 toasterparty/mechabellum-modding 与现有 `show-grid` / `axis-lock` 交互习惯。
- **风险：** 低–中（叠加层）。单位–单位距离需约定：最近邻 / 全部 / 同侧己方等（留给 P1 规格，避免一次做满）。
- **目录：** 新 `id`（建议 `placement-assist`）；与 `show-grid`、`axis-lock` 互补，不替代、不强制冲突。
- **开工门闩不变：** 仍须 P0 验收通过后再开本规格。

### P2 — 聊天 UX（仅图 1）

- **范围：**
  1. 新消息不强制滚到底；
  2. 点击或热键开窗，取消悬停即显；
  3. 加载阶段减少反复刷新导致输入丢失；
  4. 消息上限删除只影响触顶窗口（或按窗隔离缓冲），切换窗口不误删其他窗历史。
- **依赖：** Chat UI 逆向；与 `battle-suite`、`team-beacon`（依赖聊天窗）行为可能冲突，规格中写兼容策略。
- **风险：** 中–高（状态复杂、版本敏感）。
- **明确不做：** 外置翻译、txt 词替换（归 P4）。

### P3 — 自禁单位 / 增援（仅自己）

- **范围：** 本地黑名单；解锁与选择增援时对自己隐藏或禁用对应项；配置持久化。绝不影响其他玩家可选单位。
- **依赖：** 商店/解锁/增援 UI 钩子。
- **风险：** 中。允许路径 = 只过滤本地 UI 选项。禁止路径 = 改解锁协议、战报或服务器比对相关演算（易 Data Error）。与官方申请中的「房间双方禁单位 / 沙盒规则包」不是同一需求。
- **目录：** 新 `id`（建议 `self-unit-ban`）。

### P4 — 外置翻译 + txt 词替换

- **范围：** 聊天（或约定范围）文本的外置翻译桥；从 txt 读取词 → 替换词规则。建议两个小 Mod 或一个带独立开关。
- **依赖：** 宜在 P2 文本钩子经验之后；翻译需 API/隐私/延迟策略。
- **风险：** 中（质量、合规、误替换全局 UI 文案）。
- **开张条件：** P2 验收通过后再决定是否做、做哪一半。

## 红线（全目标）

- 不挂钩伤害、补给、结算等观察点做「顺手改演算」。
- 不做影响他人的禁单位 / 改补给（属沙盒官方通道，见 `docs/02-资料整理/官方申请/`）。
- 不在本管理器仓库塞游戏 Harmony 实现；管理器只继续做目录、风险扫描与分发。
- MelonLoader 0.7.3；目录字段与体积规则遵循 `ai-mod-standard`。

## 规格与实现流水线

```text
总路线图（本文）✓
    → 仅当上一目标验收通过后 ↓
P0 功能规格 → 计划 → 实现 → 游戏内验收 → 决定是否开 P1
P1 功能规格 → … → 验收 → 决定是否开 P2
P2 → P3 →（可选）P4
```

每一步「决定是否开下一个」由维护者确认；路线图表上的 P1–P4 是建议顺序，不是自动开工许可。

## 成功标准（路线图级）

- 任意时刻 backlog 上最多一个「实现中」的游戏 Mod 目标。
- 每个目标有独立规格、独立验收清单，互不绑票。
- 风险与 Data Error 边界在对应规格里写死，不依赖口头约定。

## 非目标

- 本文件不代替 P0–P4 的详细设计。
- 不规定具体类名、热键默认值、翻译供应商（留给各功能规格）。
- 不修改管理器功能，除非某 Mod 发布需要目录/用途字段协同（另开管理器规格）。
